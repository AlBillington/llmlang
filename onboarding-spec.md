# llmlang Onboarding & Sync — Methodology

Status: this is a procedure for an LLM to follow, not a script. There is no automated tool — extraction requires reading and understanding arbitrary code, which isn't scriptable the way the lockfile tooling is. This document is what makes that repeatable instead of re-derived each time.

## Part A — Extracting llmlang from a codebase that has none

1. **Survey, don't redesign.** Identify the real folder structure and file boundaries as they already exist, following the direct layout mapping rule in the format spec §8. Do not propose renaming or reorganizing anything at this stage — see step 8.

2. **Find each file's natural groupings.** Reflect only groupings that exist in the source structure, per the format spec §8. One class (or a flat module of functions with no class at all) is the common case — its methods become named entries directly under the file, no `Class:` layer needed. A file holding multiple classes gets one `Class:` node per class, each containing its own named entries.

3. **Write bullets faithfully, not aspirationally.** Describe what the code actually does today, not what it should do. If something is genuinely unclear from reading it, say so rather than guess — an inaccurate bullet is worse than an absent one, since it becomes a false claim the round-trip check in step 9 can't catch (the check verifies handles resolve and claims that were made hold up; it can't verify a bullet nobody wrote). If what's unclear looks like an actual bug rather than just an ambiguity, flag it with a `- ? ` bullet (format spec §4a) instead of burying the concern in prose — describe what the code does, flag it, don't fix it or decide it's fine.

3a-io. **Bookend an entry with accepts/returns, per the convention** (format spec §4b holds the full rule, including the never-state-the-return-twice check) — apply it as each entry is written, not as a separate cleanup pass afterward.

3a. **Write complete bullets, not a summary of the gist**, per the completeness principle (format spec §6) — state the exact rule/threshold/formula, not a gesture at it. A precise regular bullet still needs proving true, same as any other claim (step 10) — but that's a throwaway verification script, not a "should" bullet added to the spec; see step 7 for why those are different things.

4. **Name entries to match the real identifier.** Per the naming convention: an entry's name should be the actual method/function name in the code, not a paraphrase — `add_note`, not `AddsANoteAndReturnsAnId`. Add the required named-entry summary using the format spec §1 form. Apply the freetext hint defaults for folder/file/class headers as each header is written, not as a cleanup pass afterward — including the easy-to-miss case: a File whose direct entries are one implicit class's methods (the common single-class-per-file case, no separate Class node) gets the `class` hint on the *File* header itself, not just on genuine nested Class nodes.

5. **Preserve duplication, don't clean it up here.** If two methods look like they do near-identical things, describe each faithfully with its own bullets rather than silently merging or deduplicating. The value of extraction is partly diagnostic — visible duplication in the draft is a feature (see [the concept doc](readme.md) §5 "legacy audit" use case), and any cleanup is a separate, human-approved follow-up (extract a shared entry, add a Reference), never something decided silently during extraction.

6. **Look for cross-cutting patterns before writing them per-entry.** If the same concern (logging, error handling) shows up identically across most of a file or class's methods, don't restate it in every entry's bullets — propose an `@policy:` at the file/class/folder scope it actually applies to instead. This is itself a judgment call to flag for human sign-off, same as any other proposed addition, not something to apply unilaterally.

7. **Only add `~` bullets for existing tests.** Test bullets assert that a guarantee is worth permanently testing - that's a design decision, not a description, and extraction only describes (same principle as step 5: preserve duplication, don't silently fix it). If the target codebase has an existing test suite, its test cases become `~` bullets under the entry they test, using the format spec §4 comment-tracing rule. If there's no existing test suite, there are no `~` bullets from extraction - full stop, even for a guarantee that's obviously true and easy to verify. Describe it completely as a regular bullet instead (step 3a); the round-trip check in step 10 can still verify a regular bullet is accurate without it being asserted as a permanent guarantee.

8. **Handle layout mismatches by naming to match reality, not by overriding.** If a file's real name or location doesn't cleanly match what a "nice" Domain/Component name would look like, use the real name/location anyway (`legacy_app/notes.py` becomes `legacy_app: notes.py:`) — there is no manifest or override mechanism, and there shouldn't be one added for this (a `filemap` approach was tried and explicitly rejected — see [the concept doc](readme.md) §5). A component that genuinely can't be located produces a clear, actionable error naming exactly what to rename; that's the intended path when a name truly can't be made to match, not a side-channel to route around it.

9. **Insert exactly one handle per named entry**, using the entry summary from the format spec §1 and canonical name from the concept doc §4.1, in whatever comment syntax the language uses. Also add the matching test comments required by any `~` bullets from step 7. Nothing else in the source changes — this step adds comments only.

10. **Round-trip verify before presenting anything.** Run `build.py <file>.llm` then `--check` against the newly annotated code — every entry and test bullet must check clean, no `SPEC_DIVERGED` or `CODE_DIVERGED`. If a pre-existing test suite exists, it must still pass unchanged (only comments were added, no behavior touched — a failure here means something in the extraction was wrong, not the original code). If no test suite exists, write a throwaway script asserting each regular behavioral claim against the real code and confirm every one holds — never present an unverified claim as if it were checked.

11. **Present as a draft, not a fait accompli.** The extracted llmlang, the annotated source, and a passing round-trip check go to the human together, reviewed exactly like any other llmlang change — never silently trusted as the new source of truth just because extraction succeeded mechanically.

## Part B — Syncing when llmlang and code already exist and diverged

1. **Run `--check`.** It surfaces exactly two kinds of result: `SPEC_DIVERGED` (the llmlang side moved — an entry's own bullets changed, it's brand new, or an upstream policy covering it changed) and `CODE_DIVERGED` (the code side moved with no corresponding spec change to explain it).

2. **`SPEC_DIVERGED` → llmlang is the source of truth.** If it's the entry's own bullets that changed, regenerate the entry's code to match its current text. If doing so requires a decision the bullets don't resolve, that's the mapping-requirement case from [the concept doc](readme.md) (§3.2) — propose the addition to llmlang first, don't decide silently. If it's flagged because an upstream policy changed rather than the entry's own text, compare the entry's current code against the new policy wording and judge whether it still complies — most of these turn out to need nothing, that's expected and fine (the whole mechanism is tuned to prefer over-flagging for review over missing something), not a sign the check is too noisy.

3. **`CODE_DIVERGED` → investigate before regenerating.** Since hand-editing code is explicitly out of scope for this design (§1 of [the concept doc](readme.md) — llmlang is the layer people edit), this usually means something broke unexpectedly rather than an intentional change: a crash mid-write, a bad merge, an accidental edit. Look at what actually changed. If it's genuinely accidental, regenerate from llmlang to discard it. If it turns out to reflect a real, intentional change nobody captured in llmlang, propose the missing llmlang update *first* — never let an undocumented code change quietly become the new accepted truth.

4. **Rebuild and re-check before calling it done.** After resolving anything above, run `build.py <file>.llm` to record the new state, then `--check` again to confirm clean.

3b. **Name the entry, don't just describe its effect, whenever a bullet crosses into another entry.** "Redraws every print bay's appearance" is true but hides that it works by calling `updatePrintBays` - without the name, the dependency graph between entries stops being readable at a glance, which was the entire point of the `uses X` convention. This is easy to lose specifically during *later* editing passes (tightening for completeness, stripping should-bullets) that focus on one bullet at a time and don't re-check whether a name got edited out along the way - it's worth a dedicated re-read of the whole file for this specifically, not just trusting each edit was self-contained.

## Lessons from a real run (3dprinter-tycoon/Printer.js)

- **Folder paths in llmlang are relative to where the `.llm` file itself lives, not to any repo root.** Placing `printer.llm` inside `3dprinter-tycoon/` and then declaring `3dprinter-tycoon:` as the top-level folder in it double-counts the path and fails to resolve. Declare only what's *below* the `.llm` file's own location.
- **File-level coverage needs a mechanical check, not just intent.** On a 16-file project, one file (`inventory.js`) was missed entirely from both the llmlang and the handles — not caught until asked "did you cover everything" a second time, after already having missed constructors once in the same session. Trusting memory of "which files I already read" doesn't scale past a handful of files. Fix: after extraction, grep the file's own `.ext:` headers and diff that list against the original directory survey from step 1 — don't rely on recalling the list correctly.
- **The "trivial fields don't need declaring" carve-out is easy to over-apply.** On the first real extraction, an entire constructor went completely unmapped — no handle, invisible to llmlang — because its fields got waved off as "just config/state." That carve-out is for simple pass-through accessors, not license to skip real constructors wholesale. Check: does *every* real block of code in the file trace to some entry's handle? If a constructor holds meaningfully mutated state (not just stored-once config), give it its own entry named `constructor` (matching the real identifier), covering both what it stores and what it tracks.
- **Dynamic verification (step 10/11) can be blocked by something entirely unrelated to the extraction.** Real code found in the wild broke on a pre-existing circular import the moment the target module was loaded at all — nothing to do with the bullets being wrong. When this happens: don't silently skip verification and present the claims as checked anyway. Report the blocker plainly, and treat fixing it (if the human agrees) as a genuinely separate change from the onboarding itself — reviewed and committed independently, not bundled into "here's your extracted llmlang."
